Stage 1 · Observe, so nothing breaks

          

            Every project starts here. What the hook sends is judged and recorded, and the agent is not stopped; a call

What the hook changes

      

        The scenarios on the dashboard build their own payloads and then refuse them. That proves the gates run; it intercepts
        nobody. This hook is the difference: the agent runs it before every matched tool
        call and hands it the call it is about to make. The hook asks this service and, on a refusal, answers in the format that
        agent reads as a deny. On an approval it prints nothing, so the agent's own permission prompts run exactly as before.

The installer · scripts/threefold_install.py

            

              It is a file in the Threefold repository, standard library only, run once for each repository you want governed.
              --api-key-file is needed only where the stack enforces a key, and it names a file
              holding the key, so the key itself never appears in a command line or in the repository.
            

            

              

              
            

          


          

            
What it writes

            
    
              
  • .threefold.json at the repository root, holding project, endpoint, mode and, when given, api_key_file: the path to the key, never the key.
    • 
              
  • The three agents' hook settings: .claude/settings.local.json for Claude Code, .codex/hooks.json for Codex and .agents/hooks.json for Antigravity, the same blocks as Step 2 below.
    • 
              
  • The pre-commit hook, so an edit that got past an agent is still judged when it is committed, and recorded with agent pre-commit.
    • 
              
  • Every one of them listed in .git/info/exclude, which is local to your clone. None of it is ever committed, and the governed repository shows no change.
    • 
            

            

            

              The hook reads each setting from the environment first, then from .threefold.json,
              then from ~/.threefold/config.json, so a variable set where the agent starts wins
              over the file.
            

          

        


        

          

            
From observe to enforce

            

              In observe every call the hook sends goes as dry_run:
              the service judges and records it, never refuses it and never halts the session, so the enforcement console shows
              what would have been stopped while nobody is. Two things are decided on your machine before anything is sent, so
              they hold in either mode: a call carrying a credential is still refused on your machine and never sent, and a call
              the hook holds back (outside the project, a data file, a term on your never-send list) is neither sent nor
              recorded. When that record reads right, switch the repository by running the installer again
              with --mode enforce, or by setting
              "mode": "enforce" in .threefold.json.
              The next call is judged for real.
            

            

          


          

            
Uninstall

            

              Run the installer with --uninstall for the same repository. By hand it
              is the same list in reverse: delete .threefold.json, take the Threefold block out of
              each of the three hook settings files, remove the pre-commit hook, and delete the lines it added to
              .git/info/exclude.
            

            

          


          

            
Codex reads project hooks only in a trusted project

            

              Codex loads a project's hooks only when that project is trusted in Codex. Until you trust the repository there,
              .codex/hooks.json is not read and Codex's edits meet Threefold at commit time only,
              through the pre-commit hook.

What leaves your machine

        
What the hook sends, what it holds back, and why. Read this before Step 2.

      

      

        

          
Sent, for a call that passes the checks on the right

          
One POST /evaluate-tool-call with these fields and no others:

          
    
            
  • session_id
    • 
            
  • project_name: your THREEFOLD_PROJECT alias. A name that does not match the stack's pattern (Acme- and up to 40 letters, digits or dashes by default) is stored and counted as unlabelled, and the answer says so in warnings.
    • 
            
  • developer: anonymous, or a 12-character hex hash computed on your machine. Never a user name. Any developer value is shown in public only as a short hash.
    • 
            
  • tool_name, action_type and arguments. For a write, the arguments include the text being written: that text is what the gates read.
    • 
            
  • agent: claude-code, codex or antigravity; origin: hook; explain: false, so the hook does not ask for the model's sentence.
    • 
          

        

        

          
Never sent

          
    
            
  • A tool call whose target does not resolve inside the project root. The service governs the project, not the rest of your disk.
    • 
            
  • Paths under an agent's own configuration or memory: ~/.claude, ~/.codex, ~/.gemini. Those hold your instructions and history for the agent, not project code.
    • 
            
  • Data files, recognised by extension and by directory. The gates judge code; a data file is where records live.
    • 
            
  • Any call containing a term from your never-send list. You name what must not leave, in never_send.txt, and the hook checks it before it sends anything.
    • 
          

          
A call held back is not sent, so it is not checked.

        

        

          
Kept on your machine

          

            The never-send list, your project aliases and the list of governed repositories live in
            ~/.threefold/, or wherever THREEFOLD_HOME
            points. They are read there by the hook. Of the three, only the alias you set for this project appears in a request,
            as project_name.

Environment

        

          

            
              

                Variable
                Needed
                Effect
              

            
            
              

                THREEFOLD_PROJECT
                required
                The name this project is sent under, as project_name. Use an alias in the Acme- style, never the real name: it is what the console and the metrics show.
              

              

                THREEFOLD_DEVELOPER
                optional
                Who you are, for the per-developer counts. The hook hashes it on your machine and sends only the 12-character hash; unset, it sends anonymous.
              

              

                THREEFOLD_FAIL_CLOSED
                optional
                Set to 1 to refuse the call when the service cannot be reached. Unset, an unreachable service means the hook prints nothing and exits 0.
              

              

                THREEFOLD_HOME
                optional
                Where the hook's local files live, ~/.threefold unless set. never_send.txt goes there and holds the terms you never want sent: a call containing any of them is never sent.
              

              

                THREEFOLD_ENDPOINT
                optional
                The service the hook asks. The snippets on this page set it to the endpoint in the bar above.
              

            
          

        


        

          
It fails open, and silently

          

            If the service times out or the network drops, the hook prints nothing and exits 0, so the agent carries on as if
            Threefold were not installed, and nothing on screen says the call went unchecked. That is a deliberate trade: a guard
            that bricks the agent on a hiccup gets uninstalled by lunchtime. Where the risk is worth the interruption, set
            THREEFOLD_FAIL_CLOSED=1 and the same failure refuses the call instead.
          

        

      


      

        

          
The contract, both directions

          
            /evaluate-tool-call in the spec ↗
          
        


        

          
Claude Code writes this on stdin

          
{
  "session_id": "0f3c…",
  "tool_name": "Write",
  "tool_input": {
    "file_path": "src/acme_billing/domain/invoice.py",
    "content": "from boto3 import client"
  }
}

          
Codex and Antigravity hand over the same call in their own tool names; --agent tells the hook which shape to read.

        


        

          
The hook writes this on stdout when it refuses

          
Claude Code and Codex:

          
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Threefold refused this call. …"
  }
}

          
Antigravity:

          
{
  "decision": "deny",
  "reason": "Threefold refused this call. …"
}

          
When it approves, and when the service cannot be reached without THREEFOLD_FAIL_CLOSED=1: nothing at all, and exit 0.

Verify without an agent

          

            

            
          

          

            Each command makes its own session id when it runs, so two people pasting the same text never share a session and
            one reader's third call cannot halt the session the next reader lands on. A refused call never enters the session's
            history, so repeating the boundary violation is refused for that reason every time and never reaches the loop gate.
            The last command is the one that halts a session.
