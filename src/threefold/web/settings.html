Where a saved policy lives

A saved policy is written to DynamoDB under CONFIG#policy and read back when a cold Lambda container starts, so a change made here outlives the container that accepted it. If that write fails, the service keeps the value in process memory only and the next container starts on the previous policy.

What these numbers change, and what they do not

Two are applied to the gates

Saving sets the loop detector's repetition threshold from monomorphic_repetition_threshold and the breaker's single-call cap from max_single_call_usd. Raise the threshold to 5 and the first scenario on the dashboard no longer halts on the third call: that is the quickest proof this page reaches the evaluator the gate uses. The cap is weighed against caller-declared token counts, so a caller that declares zero tokens is not stopped by it.

Two are stored and reported only

max_session_budget_usd and loop_history_window are persisted, re-read on a cold start and returned by this endpoint, but no gate reads them: the session ceiling comes from each call's own budget_usd, and the detector's cycle search length is compiled in. They are shown because hiding an unwired setting is how a dashboard starts lying.
